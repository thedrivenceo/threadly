## Security model

Post Companion's security is built on these layers:

1. **Authentication and password policy** with email verification, strong passwords, and leaked password detection
2. **Supabase Auth** for user identity and session management
3. **Row Level Security (RLS)** for user-level data isolation
4. **Active profile scoping** with `threads_user_id` for connected Threads accounts
5. **Per-profile webhook secrets** for secure external integrations
6. **Server-side plan checks** for AI, URL import, webhooks, and scheduling limits
7. **Rate limiting and input validation** on AI generation and URL import
8. **Signed OAuth state** for Threads OAuth protection
9. **Admin access controls** via environment variables

## Active profile isolation

A user can connect multiple Threads profiles. Post Companion stores the active profile in `threads_profiles` and scopes profile-specific data by `threads_user_id`.

Profile-scoped tables and features include:

- `posts`
- `content_categories`
- `inspirations`
- `voice_of_customer`
- `user_settings`
- `user_templates`
- `user_writing_samples`
- `user_prompts`
- `follower_history`

This keeps content, categories, goals, inspiration, brand voice, templates, analytics, and webhook secrets separate for each connected profile.

<Callout kind="success">
  Switching profiles updates the Dashboard, Calendar, Content Bank, Goals, Categories, Inspiration, and brand settings to the active profile.
</Callout>

## Per-profile webhook secrets

Every active Threads profile has its own cryptographically generated webhook secret. External tools use that secret to send content into the profile's Content Bank.

### How it works

- A 32-byte hex secret is generated for the profile settings row
- The secret is stored in `user_settings.webhook_secret`
- The secret is unique across non-empty webhook secrets
- The `webhook-create-post` function looks up the profile by secret
- The secret must be sent in the `x-webhook-secret` header

```bash
curl -X POST https://api.postcompanion.app/functions/v1/webhook-create-post \
  -H "Content-Type: application/json" \
  -H "x-webhook-secret: your_unique_secret_here" \
  -d '{"content": "Your post text"}'
```

## Webhook secret rotation

Users can regenerate a webhook secret from Settings. The old secret stops working immediately.

Use rotation when:

- A secret was pasted into the wrong tool
- A team member should no longer have webhook access
- A Make, Zapier, or custom automation was compromised
- You want to rotate secrets as part of a regular security review

See [API Key Rotation](/security/api-key-rotation) for the full procedure.

## AI generation hardening

AI generation is protected by server-side checks.

| Control | Behavior |
|---------|----------|
| Authentication | Requires a signed-in user |
| Plan access | Requires Pro, Team, or admin access |
| Profile access | Requires an active Threads profile |
| Daily limit | 100 generations per active profile |
| Input size | Rejects very large prompts before calling Anthropic |

## URL import hardening

URL import is protected before the app fetches external content.

| Control | Behavior |
|---------|----------|
| Authentication | Requires a signed-in user |
| Plan access | Requires Pro, Team, or admin access |
| Rate limit | Limits imports per active profile |
| URL validation | Allows only public `http` and `https` URLs |
| Private network protection | Blocks localhost, private IPs, and private DNS targets |
| Response limits | Enforces timeouts, redirect limits, content type checks, and page size limits |

## Threads OAuth security

Threads OAuth uses signed state validation.

- `threads-auth-login` validates the signed-in user inside the function
- The function signs a state payload with `THREADS_OAUTH_STATE_SECRET`
- `threads-auth-callback` verifies the state signature and expiry before storing tokens
- The callback accepts Meta redirects without a Supabase auth header because Meta calls it directly

The OAuth functions are configured with Supabase gateway JWT verification disabled, then they apply their own checks:

```toml
[functions.threads-auth-login]
verify_jwt = false

[functions.threads-auth-callback]
verify_jwt = false
```

<Callout kind="info">
  This configuration is required for the Meta callback. The callback still requires a valid signed state before it writes any account data.
</Callout>

## Secrets management

All sensitive credentials are stored as Supabase secrets or platform environment variables.

| Secret | Purpose | Set via |
|--------|---------|---------|
| `ANTHROPIC_API_KEY` | Claude AI content generation | `supabase secrets set` |
| `THREADS_APP_ID` | Meta App ID for OAuth | `supabase secrets set` |
| `THREADS_APP_SECRET` | Meta App Secret for OAuth | `supabase secrets set` |
| `THREADS_OAUTH_STATE_SECRET` | Signed OAuth state protection | `supabase secrets set` |
| `ADMIN_EMAILS` | Backend admin access | `supabase secrets set` |
| `ALLOWED_REDIRECT_ORIGINS` | Allowed OAuth app origins | `supabase secrets set` |
| `SUPABASE_SERVICE_ROLE_KEY` | Server-side privileged database access | Supabase managed |
| `VITE_ADMIN_EMAILS` | Frontend admin navigation | Vercel environment variable |

<Callout kind="danger">
  Never commit `.env` files or real secrets. If a secret appears in source code or logs, rotate it immediately.
</Callout>

## Edge function authentication

| Auth method | Used by |
|-------------|---------|
| User JWT checked inside the function | Threads auth login, content generation, profile, insights, publishing |
| Per-profile webhook secret | webhook-create-post, save-inspiration |
| Signed OAuth state | threads-auth-callback |
| Meta webhook verification token | threads-webhook subscription verification |
| Service role for cron | auto-publish, sync-followers |
| Admin email check plus JWT | admin-dashboard, admin-reset-password |

## Security checklist

- [ ] `.env` is in `.gitignore`
- [ ] No API keys in source code
- [ ] RLS enabled on user-facing tables
- [ ] Profile-scoped tables filter by `threads_user_id`
- [ ] Service role key only used in edge functions
- [ ] Webhook secrets generated per profile and sent only in headers
- [ ] Webhook secret rotation available in Settings
- [ ] AI generation gated and rate-limited server-side
- [ ] URL import blocks private networks and large responses
- [ ] OAuth state signing configured with `THREADS_OAUTH_STATE_SECRET`
- [ ] Admin emails set in frontend and backend environments
- [ ] OAuth and webhook functions deployed after security config changes
- [ ] API keys rotated on schedule
