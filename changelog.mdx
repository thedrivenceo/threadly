<Update label="2026-05-29" description="v2.0.13" tags={["Feature", "Improvement"]}>
  ### Calendar: Multi-Platform Posts

  The Calendar now shows Substack, Email, Instagram, and Facebook posts alongside Threads, with each one labelled by its channel so you can see at a glance what each scheduled item is.

  - Non-Threads posts in compact calendar cells show a short channel label prefix (such as `SUBSTACK` or `IG REEL`) before the preview text.
  - In the list view, non-Threads posts now show a kicker line above the body with the channel and content ID, such as `SUBSTACK · UR-SS042`.
  - The preview body uses the most useful field per channel: Substack shows the post title, Email shows the subject line, Instagram and Facebook show the caption.
  - Threads cards look identical to before. Nothing changes for existing Threads workflows.

  This is the visual half of the multi-platform Calendar. Brand profile views, create dialog support for non-Threads content, and the edit modal are still Threads-only in this release and will land as later updates.
</Update>

<Update label="2026-05-29" description="v2.0.12" tags={["Improvement"]}>
  ### Post Companion MCP: Multi-Platform Read Surface

  The existing MCP read tools now return the multi-platform schema fields introduced in v2.0.10. External tooling can finally see Substack, Email, IG, and FB content alongside Threads through the same query surface.

  - `list_recent_posts` now returns `content_type`, `payload`, `content_id`, `external_id`, `archive_state`, and `published_at` in addition to the existing fields. A new optional `contentType` argument filters results to a single platform.
  - `list_scheduled_posts` returns the same new fields. The status filter is widened from `scheduled | pending` to `scheduled | pending | approved`, so newly approved posts surface in the scheduling view.
  - `list_content_bank_items` returns the same new fields and gains the same optional `contentType` filter.

  ### Post Companion MCP: External Push Queue

  A new tool exposes the queue of content that local bridge skills need to push to its target platform.

  - `list_pending_external_pushes(threadsUserId, contentType?, limit?)` returns posts where `status` is `approved` or `scheduled` AND `external_id` is `NULL`. Read-only; no feature flag required.

  This is the queue the upcoming local bridge skills poll. The first bridge — `pc-substack-bridge` — picks up Substack content from this queue, creates the draft via the local Substack MCP, and calls `update_post(externalId=...)` to close the loop. The same pattern applies to future Email, Instagram, Facebook, and Threads bridges.
</Update>

<Update label="2026-05-29" description="v2.0.11" tags={["Feature", "Improvement"]}>
  ### Post Companion MCP: Write Tools

  The MCP now supports write operations alongside the existing read tools. This unlocks the workflow where content created in external tools (such as Claude Code) can be pushed into Post Companion directly, without a manual capture step.

  All write tools are gated by the `mcp_multi_platform` feature flag and are off by default for all users. Admins enable the flag per user as part of staged rollout.

  - `create_post(threadsUserId, contentType, content, payload?, contentId?, status?, scheduledDate?, scheduledTime?, topic?, categoryId?, externalId?, threadId?, threadOrder?)` creates a post of any supported content type. `contentType` defaults to `threads` so existing callers continue to work.
  - `get_post(id)` fetches a single post by id, scoped to the current Threads profile.
  - `update_post(id, fields...)` performs a partial update on a whitelisted set of fields (content, payload, contentId, externalId, topic, categoryId, status, scheduledDate, scheduledTime).
  - `approve_post(id, scheduledDate?, scheduledTime?)` advances a draft or pending post. When a schedule is provided it moves straight to `scheduled`. Otherwise it sits at `approved` until a separate `set_schedule` call.
  - `set_schedule(id, scheduledDate, scheduledTime?)` sets the schedule and moves the post to `scheduled`.
  - `cancel_post(id)` marks the post as `cancelled`. The row is preserved for audit; nothing is deleted.

  Input validation rejects unknown `contentType` and `status` values at the MCP layer with clear errors. Bad values never reach the database. All writes remain scoped by `(user_id, threads_user_id)` to match existing row-level security.

  ### Post Companion MCP: Archive Tools

  Three new tools coordinate with external archives that hold a copy of every published post. The sweep runs on the archive client, reads pending items from Post Companion, archives them, and reports success or failure back.

  - `list_pending_archive(threadsUserId, limit?)` returns posts where `status = published` and `archive_state = pending`, ordered by `published_at` ascending.
  - `mark_archived(id)` flips `archive_state` to `archived` after a successful archive.
  - `mark_archive_failed(id, reason?)` flips `archive_state` to `failed` and stashes the failure reason in `payload.archive_error` for later debugging.

  ### auth_status Response

  `auth_status` now reports `mode` as `read_write` when the calling user has write tools enabled via the feature flag, and `read_only` otherwise. A new `writeToolsEnabled` boolean is also returned so MCP clients can branch on the tools available to them.
</Update>

<Update label="2026-05-29" description="v2.0.10" tags={["Improvement"]}>
  ### Foundation: Multi-Platform Posts Schema

  The `posts` table now supports content types beyond Threads. This is foundational work for the upcoming Content OS evolution. Your Threads workflows continue unchanged today, while the data model is ready for Substack, Email, Instagram, and Facebook posts in upcoming releases.

  - New `content_type` column on `posts` defaults to `threads` for backward compatibility, with support for Substack, Email, Instagram (Reel, Carousel, Photo), and Facebook (Reel, Carousel, Photo, Text)
  - New `payload` JSONB column carries platform-specific fields (titles, subjects, media URLs, slide URLs, body blocks)
  - New `external_id` column stores the platform's post ID after publish
  - New `content_id` column links posts to external content registries (such as a content library naming convention)
  - New `archive_state` column tracks sync state for posts that need to land in an external archive (such as an Obsidian content library)
  - New `published_at` timestamp separates actual publish time from scheduled time
  - Status enum extended with `approved`, `failed`, and `cancelled` for richer lifecycle tracking

  ### Foundation: Feature Flag System

  A new `feature_flags` table lets new code paths ship to production behind per-user flags, so beta features can be dogfooded by specific users before general release.

  - `feature_flags` table with `key`, `description`, `enabled_global`, and `enabled_for_users` fields
  - `is_flag_enabled(flag_key, user_id)` helper function used by edge functions to gate logic
  - Four starter flags seeded for the Content OS rollout: `content_os_v1`, `mcp_multi_platform`, `meta_direct`, and `email_v1`
  - Unknown flag keys return `false` (fail-closed)
</Update>

<Update label="2026-05-25" description="v2.0.9" tags={["Improvement", "Fix", "Security"]}>
  ### Threads OAuth Connection Fix

  Adding a new Threads profile now works from `app.postcompanion.app`. The OAuth functions explicitly allow the app domain and the callback can receive Meta redirects without a user auth header.

  - `threads-auth-login` accepts `app.postcompanion.app` as a redirect origin
  - `threads-auth-callback` verifies the signed OAuth state after the Supabase gateway allows the callback through
  - The app now surfaces clearer Threads connection errors when a function returns a specific message

  ### Webhook Security and Profile Isolation

  Webhook and profile-scoped data handling are stricter across the app.

  - Webhook URLs now use `https://api.postcompanion.app/functions/v1/webhook-create-post`
  - Webhook secrets must be sent in the `x-webhook-secret` header
  - You can regenerate a webhook secret from Settings for the active profile
  - Content Bank, Calendar, Categories, Inspiration, Voice of Customer, templates, and writing samples now guard updates and deletes by active Threads profile

  ### Endpoint Hardening

  AI generation and URL import now enforce server-side access and usage checks.

  - AI generation requires a signed-in Pro, Team, or admin user and an active Threads profile
  - URL import requires a signed-in paid user, validates public URLs, limits request size, and rate-limits imports per active profile
  - Build and lint checks now run cleanly with less noisy project defaults
</Update>


<Update label="2026-05-25" description="v2.0.8" tags={["Feature", "Improvement", "Fix", "Security"]}>
  ### Multi-Account Per-Profile Data

  All views now scope to the currently active Threads account. Switching accounts from the sidebar dropdown immediately refreshes the Calendar, Content Bank, Dashboard, and Goals pages without a manual page reload.

  - Calendar, Content Bank, Dashboard, and Goals only show posts for the active profile
  - New posts are tagged to the active profile at creation time
  - Switching accounts in the sidebar now live-updates all open pages

  ### Calendar: Drag and Drop Rescheduling

  Posts can now be dragged from one date to another directly on the calendar. Drop onto a date to reschedule, or drop onto a specific time slot to reschedule and set the time in one action.

  ### Edit Thread: Threadstorm and Character Limit

  - **Add post to thread**: an "Add post to thread" button at the bottom of the edit modal lets you expand any single post into a multi-post threadstorm
  - **Remove posts**: each post shows a Remove button when the thread has more than one post
  - **500-character limit**: a live counter (`x/500`) appears below every textarea, turning orange above 400 and red above 500. Saving is blocked if any post exceeds the limit.

  ### Security Hardening

  - **Webhook verification**: inbound webhook requests are now validated against your per-user webhook secret. Requests with an invalid or missing secret are rejected with a 403.
  - **Webhook secret rotation**: you can rotate your webhook secret from Settings without affecting existing scheduled posts.
  - **AI generation**: rate limiting and input validation tightened on the AI generation endpoint.
  - **URL content import**: stricter URL allowlist and input sanitisation on the import endpoint.
  - **Threads OAuth**: state parameter validation added to the OAuth callback to prevent CSRF attacks.

  ### Bug Fixes

  - Fixed posts being attributed to the wrong Threads profile after connecting multiple accounts (incorrect backfill at migration time)
  - Fixed Dashboard and Goals showing posts from all accounts during initial profile loading
  - Fixed a crash on the Dashboard page on first load
</Update>
